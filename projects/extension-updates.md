# 浏览器扩展升级：把上线后的维护设计成流程

[返回作品集首页](../README.md)

## 产品位置与问题

这是浏览器采集工具的配套升级服务，展示产品上线后的版本运营与错误预防实践。业务工具发布后仍需要持续更新；安装包、版本记录和更新地址若分散维护，可能出现错误覆盖、版本倒退或包与地址不一致。

服务将“发布 → 校验 → 记录 → 浏览器获取更新”集中到独立流程。本案例关注交付与维护能力，服务本身不包含 AI 模型功能。

## 用户路径与设计选择

发布者在管理页填写版本、扩展 ID、说明和发布令牌，上传已签名 CRX，随后查看结果与历史；也可使用命令行工具。浏览器通过更新清单获取版本和下载地址。业务 Web 与升级服务独立部署。

| 设计问题 | 当前选择与取舍 |
| --- | --- |
| 重复点击或重试怎么办 | 同版本同文件返回已有结果，减少重试歧义 |
| 如何阻止误覆盖 | 同版本不同文件拒绝覆盖，较旧版本拒绝发布 |
| 如何核对发布内容 | 校验 CRX 结构、公钥推导的扩展 ID、Manifest 版本与更新地址，保存 SHA-256 |
| 并发发布如何落盘 | Linux 文件锁串行化写入，单文件原子替换；多个文件之间不具备数据库事务保证 |

发布接口校验管理员令牌，浏览器更新清单和下载入口允许匿名读取。签名私钥由发布方独立保管；当前实现的 CRX 解析与 ID 校验不包含完整的密码学签名验证。

## 验证证据与边界

现有 8 项测试覆盖发布权限、管理页面、更新清单、下载、幂等和版本规则。2026-10-12 在 Windows / Python 3.12 迁移检查中，**4 项通过、4 项失败**，失败来自发布锁依赖 Linux `fcntl`。完整发布应在 Linux、WSL 或 Docker 验证，本次未完成相应环境的全量测试。

测试使用模拟 CRX，未验证真实浏览器安装、签名或企业策略。发布文件需持久存储，当前建议单实例；仓库不包含安装包、私钥或运行记录。
